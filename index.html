Binary Inspection & Prompt Specification

Antigravity 的内置提示词里装了什么，我们可以怎样精简它？

打开本机 Antigravity 的语言服务器二进制文件，可以看到 Go embed.FS 里嵌着 13 个提示词模板（桌面端共 22,363 字，IDE 扩展共 31,959 字）。其中超过一半的篇幅在规定如何往 brain/ 目录写外部报告、开局强制检索旧知识库摘要，以及在回复末尾向用户推销斜杠命令。

我们构建了独立的轻量 Rust 工具箱 agy-tool，支持原位精简提示词、解锁 983,040 token 上下文上限，并在输入框底部注入上下文与生成速度查看器。向下滚动页面，即可逐步查看全部 13 个模板的拆解与运行期演进。

下载 agy-tool.exe (v1.0.0) ↗ 开始逐步拆解 ↓

一份系统提示词由 13 个独立模板拼成

在 Antigravity 客户端里，每次你向模型发送一条消息，后端的 language_server 都会把 13 个内置的 .tmpl 模板、19 个原生工具的 Protobuf 定义以及你的工作区规则拼成完整的系统提示词。

通过调用本机语言服务器的 GetCascadeTrajectoryGeneratorMetadata 接口，可以看到服务端真实的分词账本：仅 artifacts.tmpl（要求把总结写进外部文件）、persistent_context.tmpl（要求开局先查本地旧知识库）、conversation_transcript.tmpl 和 slash_commands.tmpl 等几个模板，每轮就要占掉数千 token。

随着你向下滚动页面，右侧固定舞台会一步步展示这 13 个模板槽位在二进制里的真实大小、各自原本的作用，以及在不同精简档位下哪些被清零、哪些被修改。点击舞台上的任意方块，下方抽屉会实时对比修改前后的原文。

        Runtime 01 / 04 · 默认上限截断
        
为什么百万窗口默认只能用到 256K / 128K？

        

          通过反汇编 language_server 的 .gopclntab 符号表可以看到：模型本身的物理窗口虽为 1M，但内核在两处独立位置硬编码了 256,000（0x3e800，IDE 端为 128,000）上限：
        

        

          第一处是 utils.GetCheckpointConfig 中的 cmovb 封顶指令（控制何时触发自动压缩）；第二处是 DefaultSerializer.populateContextWindowMetadata（控制写进会话数据库与前端的 maxContextTokens 显示值）。
        

        
          原版状态：自动压缩与前端显示均锁死在 256,000 token
        
      


      

        Runtime 02 / 04 · 双点位机器码解锁
        
同步解除压缩封顶与前端显示限制

        

          当在工具箱中选择「解锁 900K / 1M」时，agy-tool 会同时修改这两处机器码：将 GetCheckpointConfig 的 cmovb 封顶指令改为 mov + 6×NOP 直通，并将 populateContextWindowMetadata（@35359739）的写入值改为 983,040（0xf0000）。
        

        

          即使客户端正在运行，工具箱也会利用 Windows 允许对运行中 .exe 同目录改名的特性免杀进程写入新内核，并通过 CDP 将新上限实时同步给已打开的窗口。
        

        
          解锁后：物理可用窗口扩展至 983,040 token (3.84 倍)
        
      


      

        Runtime 03 / 04 · 底部双胶囊分离设计
        
挂载于 Request Review 左侧，独立小字悬停

        

          旧版第三方插件挂载在窗口右上角，容易被 Windows 原生窗口控制按钮遮挡。我们将状态栏移至底部输入栏 Request Review 按钮正左侧，并拆分为两个独立按钮：
        

        

          左侧默认只显示 13px 进度圆环（不展示数字文字，保持输入栏干净），鼠标悬停时只显示具体数值与占用比；右侧去掉闪电图标，直接显示 tok/s，悬停显示综合速度、流式速度与首字耗时（TTFT）。
        

        
          看右侧舞台：演示独立悬停小字气泡
        
      


      

        Runtime 04 / 04 · 原生分词账本与路由监控
        
点击展开三部分明细，监控真实返回 model id

        

          点击圆环或速度胶囊，会向上弹出紧凑详情面板：直接读取服务端返回的 System Prompt（精确到 identity、guidelines、skills 等子项）、Native Tools 与 Chat Messages 分词账本。

          RULE 01 · guidelines.tmpl
          针对现象：未读源码凭印象断言
        

        
未读源码前禁止凭印象断言代码内容

        

          原版 guidelines.tmpl 仅有保留注释与不越界沙箱两条规定，未要求模型在讨论代码前先读文件。我们明确加入：凡未在本会话通过 read_file 读取过的文件、符号或配置，禁止凭印象断言。
        

        
Never make confident claims about files, symbols, or configs you have not read via `read_file`.

      


      

        

          RULE 02 · guidelines.tmpl
          针对现象：顺手改写大段无关代码
        

        
最小改动原则（优先删减冗余分支与包装）

        

          针对模型修改代码时容易顺手改写大段无关代码的倾向，在 guidelines.tmpl 中明确要求只触碰最少必要行数，优先通过删减冗余分支或包装层解决问题，保留无关注释与格式。
        

        
Make the smallest correct change. Prefer deleting branches or wrappers over adding new layers.

      


      

        

          RULE 03 · function_call.tmpl
          依据：Google 官方《Argon 开发者指南》
        

        
工具调用前不输出非结构化引导语或冒号

        

          Google 官方开发者指南建议："avoid unstructured text before tool calls"。我们在 function_call.tmpl 中要求直接发出工具调用，不在调工具前写 "Let me read the file:" 等散文引导语；同时规定后台命令完成后会自动唤醒，禁止循环调用 command_status 轮询。
        

        
Emit tool calls directly without unstructured prose preambles or trailing colons. NEVER poll `command_status` in a loop.

      


      

        

          RULE 04 · communication_style.tmpl
          依据：language_server @58777383 实测报错
        

        
直接在对话框交付结论，禁传 ArtifactMetadata

        

          二进制逆向证实：当对非 brain/ 目录的普通工程代码调用 edit_file / write_file 并传入 ArtifactMetadata 时，内核会直接抛 "ArtifactMetadata was provided but path is not a valid artifact path" 错误。规则明确要求直接在对话框输出分析与 Diff，不写 brain/ 报告且不传该参数。
        

        
Deliver all explanations, plans, diffs, and summaries directly in chat. Do NOT write report files to `brain/` or pass `ArtifactMetadata` when editing workspace code files.

      


      

        

          RULE 05 · communication_style.tmpl
          依据：原生 edit_file 全局替换机制
        

        
edit_file 必须携带 3~5 行唯一上下文锚点

        

          Antigravity 原生 edit_file 的实现逻辑是“若 Target 在文件中出现多次则全部替换”。规则强制要求在 Target 中包含 3~5 行未修改的上下游代码以确保全局唯一命中，且同一文件的多处修改跨轮次串行执行。
        

        
Because `edit_file` replaces every occurrence of `Target`, always include 3-5 lines of unchanged surrounding context in `Target` so it matches a single unique location.

      


      

        

          RULE 06 · communication_style.tmpl
          区分提问探讨与修改指令 + 验证闭环
        

        
区分提问（Inquiry）与指令（Directive），改后跑窄域验证

        

          遇到架构咨询或问题排查（Inquiry）时直接在对话框给出分析，不擅自改文件；遇到明确编码指令（Directive）时走完“搜索 → 最小修改 → 运行最窄范围测试/编译验证”全流程，未跑过验证禁止声称测试通过。
        

        
Treat questions/reviews as Inquiries (do NOT edit files). After editing code, run the narrowest test, typecheck, or build command via `run_command` that proves the change works.
